# Organizations and events — approved implementation contract

This feature branch is based on PR #22, as explicitly authorized. No new PR is opened.

## Organizations

- Community contains Groups / Organizations / Search tabs with common page spacing, labeled search/help, placeholders, conditional inline clear controls, and compact icon filters on web/native. Organization lists filter Admin / Invited / Accepted / Requested (own pending requests); discovery filters Groups / Organizations. Search is debounced 300 ms and requires four characters. Filters apply before server pagination.
- Events is a separate main navigation section; event creation is available only inside the owning organization to its administrator. Creation uses separate contextual pages, never a conversion or radio selector.
- Unique normalized name, 5–120 characters; mandatory logo and authenticated, verified MapTiler address. Name/logo help is in field popovers; the location uses the match-style address/favorite row. Submit stays fixed at the bottom with a send icon, no top separator, and extra bottom/safe-area clearance.
- One compact Upload command: browser file picker on web; native Camera/Photo library buttons on one row in a source sheet and system picker. No broad photo-library permission; camera permission is requested only after choosing Camera, with fresh permission/settings checks. JPEG/PNG/WebP, at most 5 MB (5,000,000 bytes); undistorted square preview, replace but no remove. MongoDB base64 assets, bounded uploads below Vercel's request limit; expired incomplete uploads cleaned up.
- One organization admin: creator, automatically confirmed member; no transfer. BGO moderators are verified freshly from Clerk `publicMetadata.bgoRole === ADMIN`, never client metadata or unverified claims. Moderator icon between notifications and profile.
- Private proposals: PENDING -> CREATED; approved edits become MODIFIED proposals. The approved revision remains operational while modifications are pending/rejected. Review shows a Manage organization label with question-mark help, a Reject reason placeholder, and icon-bearing Approve/Reject buttons on one row on both clients. Reject with reason; creator corrects/resubmits. Names are reserved across approved and proposed revisions.
- Details / Members / Events tabs on both clients. Details reuses the platform's common card frame: logo left; name/status together, icon-bearing venue with address below, confirmed-member count (including creator) and published-event count right. Counts come from authorized API reads, not loaded pages. Accepted members leave through an icon-only danger action in the page header; self-request cancellation sits bottom-right of the detail card. Invited recipients have separate icon-only Accept/Reject card actions, each confirming only the chosen action. Destructive confirmations and the admin edit FAB remain. Events embeds the searchable organization list with an admin-only creation FAB. Web tab selection is retained in the URL, including return from friend invitation.
- Approved details/published events visible to authenticated non-excluded users. Accepted members are visible only to confirmed members/admin; pending/excluded feeds are admin-only. The first row is an admin friend-invitation slot (disabled with an explanation before approval). Exhaust accepted pages (including creator first), then pending, then excluded; never fetch the whole roster. Show full name with smaller username, no email, and avatar-corner admin/request/invitation/exclusion badges.
- Member rows expose only membership controls and a vertical-ellipsis social menu, never inline follow/friend buttons. Native contacts, groups, matches and organizations reuse the common HeroUI social bottom sheet, mounted closed even before selection so the first ellipsis press produces the required closed-to-open transition. Follow/unfollow (including friends), friendship and global blocking remain menu actions. Enrichment is bounded to the authorized member page; expose viewer-owned block state, not incoming block flags. Social actions reconcile the viewer's member caches across organizations without changing membership. Repeated social submission is serialized; failure rolls back only affected social fields.
- Ordinary membership requests: any authenticated non-excluded user, no friendship requirement; admin approval. One request icon opens Accept / Reject / Ban (Accetta / Rifiuta / Banna) on one row, with each icon beside its text; Cancel (Annulla) occupies a separate row below; Ban excludes only from this organization, not a friend-request or global-block operation. An admin's outgoing invitation has one cancellation icon and explicit confirmation. An invited recipient's detail card has separate confirmed Accept/Reject choices; Members and invitation list rows retain the response icon opening Accept / Reject without revealing the private roster. Invitations: confirmed friends, acceptance confirms membership. Leaving and ordinary removal set LEFT and permit new requests/invitations. The removal confirmation offers Cancel / Remove from organization (Elimina) / Remove and exclude (Elimina-Blocca). Only explicit exclusion sets EXCLUDED until manual revoke, and only for this organization. Global social blocking is separate. None of removal, exclusion or revocation restores cancelled bookings automatically.
- No organization archival in this iteration. Existing group archival remains unchanged.

## Events and tables

- The main Events list contains the viewer's confirmed bookings, pending requests/invitations, administered events and assigned demonstrations, not every event of every joined organization. The organization's Events list retains its existing visibility. Draft privacy, exclusions and every role/action restriction remain unchanged.
- Event lists, including the organization Events tab, reuse platform event cards: locally generated DiceBear planets artwork left; approved-organization identity, event name, one local date with start/end times, venue/address, table count and confirmed-participant count right. Published has a success badge; Draft a warning badge at top-right. Participants are distinct users with CONFIRMED bookings on non-cancelled tables, not summed booking rows; pending/cancelled bookings and automatically unoccupied administrator/demonstrator roles do not contribute. Counts include retained/unloaded records and stay server-authoritative. Booking changes revalidate the owning event list; event creation/publication/update/cancellation also marks owning organization counts stale and revalidates affected active data.
- Event detail has Details / Tables tabs using the existing platform tab pattern. Details reuses the event card without organization identity or table count, retaining confirmed participants, local times/address, status and booking deadline. Tables reuse draft-card content (fixed cover, name, times, game, player limits, demonstrator and rating badge) as read-only links with confirmed/reserved counts and status; no row edit/removal. Table fetching/paging belongs to that tab. Cancel event is an icon-only danger action at the header's right; the shared edit FAB remains bottom-right across both tabs only when server modification rights and the exact cutoff allow it. Cancellation still requires confirmation and disables repeated submission.
- The Matches list replaces textual Event table tags with a labeled calendar icon below the artwork at bottom-right. The administrator crown remains above it. After filters, Table list (Lista Tavoli) and the existing question-mark popover explain both symbols; event-table cards retain the fixed-match invitation/action guards.
- Past/Future filters use the event end instant: ongoing events remain Future, and the exact end belongs to Past. Both periods start selected. Search/help/inline clear and compact icon filters follow the same platform-specific list pattern; filters are server-paginated.
- Organization admin only: information -> table editors -> review; save DRAFT or PUBLISHED. Draft admin-only. Publishing requires approved organization and at least one table. No return from published to draft.
- Match/event wizards share numbered, theme-aware step indicators. Event detail has no Back action on its first page; subsequent pages use arrow-only Next/Back FABs. Events must start and end on the same local day, strictly ordered, including when their UTC dates differ. The first step has a plain Event detail heading, specific Event name help and an example placeholder, one date-only Event date picker with help, then two native/browser time-only pickers together with shared start/end help. Changing the day retains selected wall-clock times without inventing missing times. Location uses the verified-address/favorite row (initially Choose the event address). Next stays at the screen bottom with an arrow and reserved scrolling/safe-area space. Time zone is not editable: creation uses the device/browser zone; editing retains the stored zone. The API validates it, rejects nonexistent DST wall times and preserves unchanged seconds/repeated-hour instants. Android native time pickers do not enforce min/max: invalid selections are rejected visibly without clamping or saving them.
- Location precedes the compact deadline-hours input; each has its own help. Favorite hearts resolve the selected location's status, including favorites beyond the loaded list page, before enabling toggles. Booking deadline is a positive numeric elapsed-hour offset before start, with help and a default of 24 hours. Decimal point/comma are supported; it is converted to the exact ISO cutoff required by the API. Editing derives the existing offset, preserving sub-hour/second/millisecond cutoffs rather than resetting them to 24 hours. Deadline-only changes still reschedule closure without resetting participation.
- Tables step omits event name/time zone/location and shows Event day as a date-only row, then start/end times together with icons, Tables help documenting the 20-table maximum, a compact Add table action and common empty state. Draft cards use the same fixed 80×80 cover area (including fallback), time-only start/end, icon-bearing name/game/player range and optional demonstrator nickname; enabled GLOBAL rating has a bottom-right cover badge. Editors use native/browser time-only fields on the event day, strictly after event start and before event/table end, bounded +/- players, game/member list-row selection, removable demonstrators and Save icon. Both table-editor and demonstrator-selection Back live in the screen header, never a table-editor FAB. Review uses separate icon-bearing event-name, date-only day, paired time, and venue/address rows, then Tables and the existing cards. Invalid fields retain inline errors. Existing unedited tables and precise stored instants remain intact.
- At most 20 tables per event, including retained/unloaded tables during partial edits. Add is disabled at the limit; only explicit removals free a position. API validation and transactional combined-table checks enforce the limit; no implicit deletion. Rendering remains paginated/virtualized. Each table has name, min/max (min >= 2), one game, contained start/end, optional confirmed-member demonstrator and optional per-table GLOBAL OpenSkill. Admin/demonstrator do not automatically occupy seats.
- Confirmed members only book. One booking/user/table; multiple tables in the same event allowed only at non-overlapping times. Pending invitations and self-requests reserve seats; self-requests require admin approval. No waitlist. Minimum counts confirmed players only.
- Before deadline: event name preserves bookings; date/time/location resets affected bookings; deadline reschedules closure; ANY table change resets that table, including name/demonstrator/rating flag. Removal/cancellation cancels unfinished participation. Confirm destructive resets explicitly.
- At/after deadline ALL event/table/booking/invitation/approval modifications are blocked, including admin. No post-deadline additions or reactivation. One automatic minimum check: under-minimum tables cancelled, remaining table matches PLANNING -> CREATED. Fixed choices, no votes or ordinary match planning actions.
- Leaving/removal/ban before deadline cancels bookings and demonstrator assignments. After deadline rosters stay frozen, including departed/excluded players; they can be recorded as ND. Never rewrite historical results.
- Result registration remains available after closure to admin/demonstrator; admin covers a table without demonstrator. Reuse exact-decimal ranking, ties, ND and atomic OpenSkill engine. Optional GLOBAL per game/table, never organization scope; immutable results.
- Table matches show event badge; confirmed players only. Cancelled/revoked tables disappear from match list; no cancellation history UI. Organizations are not selectable as normal match groups.

## Cross-cutting guarantees

- TanStack Query owns remote state, scoped by API URL + Clerk user ID; resolve fresh token immediately before each request. Optimistic updates for existing owned cache, cancellation before changes, action-specific default toast, rollback and danger toast; never fabricate server-authoritative IDs/outcomes.
- EN/IT localization, HeroUI web/native, accessible labels, skeletons only for uncached data, pagination/virtualization and usable cached fields during revalidation. Item/card lists reuse the platform's centered EmptyList icon/message pattern (including search/discovery, events/tables, users/friends, games, countries, addresses/favorites and notification previews); loading and failures are not empty success states. Common linked/detail card frames preserve keyboard focus, touch actions and readable long content.
- Inngest is optional for publication. Durable outbox, revision checks, idempotent transactions, signed worker endpoint and environment/database isolation remain. API enforces exact time limits even without a worker; authorized reads materialize closure after cutoff. Autonomous closure/recovery require configured Inngest; see operational gates.
- Web Playwright + native Maestro acceptance coverage, deterministic logic 100% Vitest thresholds, transactional integration/race tests. No silent skips or weakened gates.
